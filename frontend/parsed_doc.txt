ABSTRACT 
The increasing competition in the restaurant industry has made maintaining food quality and customer satisfaction more important than ever. Efficient collection, management, and analysis of customer feedback is essential for improving service standards and ensuring consistent quality. This project, titled 
“Food Quality Monitoring System in Restaurants (Customer Feedback Loop)”
, presents the design and implementation of a relational database system to effectively manage customer feedback and quality assessment processes.
The system is developed using Entity-Relationship (ER) modeling to identify key entities such as customers, restaurants, menu items, orders, feedback, ratings, staff, and quality parameters. Relationships among these entities are clearly defined with appropriate cardinalities, primary keys, and foreign keys to maintain data integrity and consistency. Dependent entities such as feedback details and order items are modeled carefully using composite keys where necessary to represent their relationships accurately. The ER model is further transformed into a relational schema, and the database is implemented using MySQL with Data Definition Language (DDL) and Data Manipulation Language (DML) commands.
To improve system efficiency and scalability, customer reviews and related multimedia files (if any) are stored externally, while only essential metadata and references are maintained within the database. The system also incorporates role-based access control to manage different user roles such as Admin, Restaurant Manager, Staff, and Customer, ensuring secure and controlled access to data.
The proposed database design ensures data consistency, reduces redundancy through normalization, supports efficient query processing, and enables effective monitoring of food quality trends. By converting raw customer feedback into structured and actionable insights, the system provides a reliable foundation for continuous quality improvement in restaurants. This project demonstrates the practical application of DBMS concepts including ER modeling, relational schema design, normalization, SQL implementation, and feedback data analysis.

1.1 Introduction
In today’s highly competitive restaurant industry, maintaining food quality and customer satisfaction is essential for long-term success. Restaurants must continuously monitor food standards, hygiene, service quality, and customer experience to retain customers and enhance their reputation. Customer feedback plays a critical role in identifying areas of improvement and ensuring consistent quality.
Traditional feedback systems often rely on manual records or unstructured digital reviews, making it difficult to analyze trends and take timely corrective action. These methods may lead to data redundancy, inconsistency, and inefficient tracking of complaints. To address these challenges, a structured database system is required.
This project, Food Quality Monitoring in Restaurants (Customer Feedback Loop), focuses on designing a relational database system using DBMS principles to efficiently store, manage, and analyze customer feedback, orders, menu items, and quality-related data.
1.2 Motivation
The motivation for this project arises from the need for a centralized system that enables restaurants to systematically monitor food quality and customer satisfaction. As the number of customers and orders increases, managing feedback, complaints, payments, and ingredient tracking becomes complex without a structured database.
Poor handling of customer feedback can result in unresolved complaints, reduced customer trust, and damage to the restaurant’s brand image. By implementing a database-driven system, restaurants can track feedback trends, monitor service performance, and improve decision-making.
This project demonstrates how database concepts such as ER modeling, relational schema design, normalization, and integrity constraints can be applied to a real-world restaurant management scenario.
1.3 Scope
The scope of the Food Quality Monitoring System includes:
● Management of users with different roles such as Admin, Manager, Staff, and Customer
● Recording customer orders and order details
● Maintaining menu items and pricing information
● Managing ingredient and recipe details
● Collecting and storing customer feedback and ratings
● Logging and tracking complaints raised from feedback
● Recording payment information
● Monitoring food quality trends through stored feedback data
The project primarily focuses on database design and implementation and does not include advanced front-end or user interface development.
1.4 Problem Statement
To design and implement a relational database system that efficiently manages restaurant operations by organizing user data, orders, menu items, ingredients, payments, feedback, and complaints while ensuring data integrity, consistency, reduced redundancy, and scalability through proper DBMS design principles.

1.7 Construction of DB Using ER Model for the Food Quality Monitoring System
The database for the Food Quality Monitoring in Restaurants (Customer Feedback Loop) system was constructed using the Entity-Relationship (ER) model as the conceptual foundation. The ER model provides a structured representation of the system, which was systematically transformed into a relational database schema.
All major entities identified in the ER model, such as User, Department, Branch, Customer_Profile, Order, Menu_Item, Ingredient, Payment, Feedback, and Complaint_Log, were mapped to relational tables. The attributes of each entity were implemented as table columns, and primary keys were defined to uniquely identify each record in the database.
Relationships between entities were implemented using foreign keys to maintain referential integrity. One-to-many relationships, such as User–Order and Order–Order_Details, were handled by placing foreign keys in the corresponding child tables. Many-to-many relationships, such as the relationship between Menu_Item and Ingredient, were resolved through the Recipe entity, which acts as an associative table. Weak entities like Order_Details were implemented with dependency on the Order entity to maintain relational consistency.
Derived attributes such as order subtotal and total amount are computed dynamically based on item price and quantity to reduce data redundancy. The database schema was implemented using SQL Data Definition Language (DDL) commands, and referential integrity constraints were enforced through primary and foreign key relationships.
This structured approach ensures data consistency, minimizes redundancy through normalization, and enables efficient data retrieval and analysis of customer feedback and food quality metrics.

2.1 Relational Schema for Food Quality Monitoring System
A relational schema represents the logical structure of the database derived from the Entity-Relationship (ER) diagram. It defines the relations (tables), attributes, primary keys, and foreign keys used to maintain relationships between tables. The relational schema is obtained by applying standard ER-to-relational mapping rules, where strong entities are converted into tables and relationships are implemented using foreign keys.
The relational schema for the Food Quality Monitoring in Restaurants (Customer Feedback Loop) system includes tables for users, departments, branches, customer profiles, orders, order details, menu items, ingredients, recipes, payments, feedback, and complaint logs. Each table contains attributes that describe the entity, along with primary keys to uniquely identify records.
One-to-many relationships such as User–Order and Order–Order_Details are implemented by placing foreign keys in the corresponding child tables. Many-to-many relationships, such as the relationship between Menu_Item and Ingredient, are resolved using the Recipe table as an associative entity. Weak entities like Order_Details are implemented with dependency on the Order table to maintain referential integrity.
Primary and foreign key constraints are defined to ensure consistency, prevent data redundancy, and maintain integrity across the database. The relational schema forms the foundation for implementing the database using SQL and supports efficient querying, reporting, and analysis of food quality and customer feedback data.

Figure 2.1 depicts the relational schema of the Food Quality Monitoring System, showing all relations along with their attributes, primary keys, and foreign key dependencies. It illustrates how Orders act as the central entity connecting Users, Order_Details, Payments, Feedback, and Branches.
The schema further demonstrates how Menu_Items are linked to Ingredients through the Recipe table, and how Feedback records are associated with Orders and may generate Complaint_Logs. Foreign key relationships ensure referential integrity between tables, while primary keys uniquely identify each record. Overall, the relational schema provides a clear logical structure of the database, highlighting how customer interactions, food quality monitoring, and complaint management are integrated within a single structured system.

CREATE TABLE Department (
    Dept_ID INT PRIMARY KEY,
    Dept_Name VARCHAR(50) NOT NULL
);

CREATE TABLE Branch (
    Branch_ID INT PRIMARY KEY,
    Phone_No VARCHAR(15),
    Street_No VARCHAR(20),
    Pin_Code VARCHAR(10),
    Address_Line VARCHAR(255)

-- 3. INGREDIENT [cite: 1181]
CREATE TABLE Ingredient (
    Ing_ID INT PRIMARY KEY,
    Ing_Name VARCHAR(100) NOT NULL,
    Stock_Quantity DECIMAL(10, 2) DEFAULT 0.00,
    Expiry_Date DATE
);
-- 4. MENU_ITEM [cite: 1187]
CREATE TABLE Menu_Item (
    Item_ID INT PRIMARY KEY,
    Item_Name VARCHAR(100) NOT NULL,
    Price DECIMAL(10, 2) NOT NULL,
    Category VARCHAR(50)
);
-- 5. USER [cite: 1196]
CREATE TABLE User (
    User_ID INT PRIMARY KEY,
    First_Name VARCHAR(50) NOT NULL,
    Last_Name VARCHAR(50),
    Email VARCHAR(100) UNIQUE NOT NULL,
    Phone_No VARCHAR(15),
    User_Role VARCHAR(20) CHECK (User_Role IN ('Staff', 'Manager', 'Customer', 'Admin')),
    Branch_ID INT,
    Dept_ID INT,
    FOREIGN KEY (Branch_ID) REFERENCES Branch(Branch_ID),
    FOREIGN KEY (Dept_ID) REFERENCES Department(Dept_ID)
);
-- 6. ORDER [cite: 1229]
CREATE TABLE `Order` (
    Order_ID INT PRIMARY KEY,
    Order_Time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    User_ID INT NOT NULL,
    Branch_ID INT NOT NULL,
    FOREIGN KEY (User_ID) REFERENCES User(User_ID),
    FOREIGN KEY (Branch_ID) REFERENCES Branch(Branch_ID)
);
-- 7. FEEDBACK [cite: 1257]
CREATE TABLE Feedback (
    Feedback_ID INT PRIMARY KEY,
    Rating_Score INT CHECK (Rating_Score BETWEEN 1 AND 5),
    Text_Comments TEXT,
    User_ID INT,
    Branch_ID INT,
    Item_ID INT NOT NULL,
    FOREIGN KEY (User_ID) REFERENCES User(User_ID),
    FOREIGN KEY (Branch_ID) REFERENCES Branch(Branch_ID),
    FOREIGN KEY (Item_ID) REFERENCES Menu_Item(Item_ID)
);
-- 8. COMPLAINT_LOG [cite: 1271]
CREATE TABLE Complaint_Log (
    Log_ID INT PRIMARY KEY,
    Status VARCHAR(20) DEFAULT 'Open',
    Resolution_Notes TEXT,
    Feedback_ID INT NOT NULL UNIQUE,
    FOREIGN KEY (Feedback_ID) REFERENCES Feedback(Feedback_ID) ON DELETE CASCADE
);
SET FOREIGN_KEY_CHECKS = 1;

ANALYZING THE PITFALLS, IDENTIFYING THE DEPENDENCIES, AND APPLYING NORMALIZATIONS
4.1 Analysing Pitfalls, Identifying Dependencies and Applying Normalization (1NF, 2NF, 3NF)
Introduction
In database design, improper structuring of data can lead to various issues such as redundancy, inconsistency, and anomalies during insertion, deletion, and updating of records. To overcome these problems, normalization is applied. Normalization organizes data into well-structured tables by eliminating redundancy and ensuring data integrity.
The Food Quality Monitoring System database was analyzed for possible pitfalls and normalized up to Third Normal Form (3NF).
4.1.1 Identifying Pitfalls
The following potential issues were identified in the initial database design:
Data Redundancy
Repeated storage of customer details, menu items, and ingredient information across multiple tables can increase storage and lead to inconsistencies. 
Update Anomalies
Updating a menu item price in multiple places may cause mismatched values. 
Insertion Anomalies
Inability to insert data without complete information (e.g., cannot add feedback without an order). 
Deletion Anomalies
Deleting an order may lead to loss of related feedback or payment details.
4.1.2 Functional Dependencies
Functional dependencies define relationships between attributes:
User Table
User_ID → First_Name, Last_Name, Email, Phone_No, User_Role 
Order Table
Order_ID → User_ID, Branch_ID, Order_Time 
Menu_Item Table
Item_ID → Item_Name, Price, Category 
Order_Details Table
(Order_ID, Item_ID) → Quantity, Subtotal 
Feedback Table
Feedback_ID → Rating_Score, Text_Comments, User_ID, Order_ID 
Complaint_Log Table
Log_ID → Feedback_ID, Status, Resolution_Notes 
4.2 First Normal Form (1NF)
First Normal Form ensures that:
● All attributes contain atomic values
● There are no repeating groups
● Each record is uniquely identifiable
Orders Table (Not in 1NF)
4.2.1 Identify Dependency
In the unnormalized relation, the functional dependency is:
Order_ID → User_ID, Branch_ID, Order_Time, Items
Here, the attribute 
Items
 may contain multiple values, which violates atomicity.
Each order is associated with multiple menu items, but storing them in a single column leads to improper dependency representation.
4.2.2 Apply Normalization to 1NF
To convert the table into First Normal Form:
● Multi-valued attributes (menu items) are separated
● Each menu item is stored in a separate row
● A new table 
Order_Details
 is created
● A composite primary key (Order_ID, Item_ID) is introduced
Converted to 1NF
4.3 Second Normal Form (2NF)
Second Normal Form ensures that:
● 
The table is in 1NF
● There are no partial dependencies
● All non-key attributes depend on the full primary key
Order_Details Table (Not in 2NF)
4.3.1 Identify Dependency
Functional dependencies:
(Order_ID, Item_ID) → Quantity, price
Item_ID → Item_Name, Price
Here, 
Item_Name
 and 
Price
 depend only on Item_ID, not on the full composite key.
This creates a partial dependency, violating 2NF.
4.3.2 Apply Normalization to 2NF
To remove partial dependency:
● Separate menu item details into a new table
● Keep only fully dependent attributes in Order_Details
Converted to 2NF
4.4 Third Normal Form (3NF)
Third Normal Form ensures that:
● The table is in 2NF
● There are no transitive dependencies
Users Table (Not in 3NF)
4.4.1 Identify Dependency
Functional dependencies:
User_ID → Dept_ID
Dept_ID → Dept_Name
This creates a transitive dependency:
User_ID → Dept_Name (indirectly)
4.4.2 Apply Normalization to 3NF
To remove transitive dependency:
● Separate department details into a new table
● Keep only foreign key in Users table
Converted to 3NF
4.5 Boyce-Codd Normal Form (BCNF)
Boyce-Codd Normal Form ensures that:
● The table is in 3NF
● For every functional dependency, the determinant must be a key attribute
● There are no anomalies due to non-key determinants
Feedback Table before  (Not in BCNF)
4.5.1 Identify Dependency
Functional dependencies in the Feedback table:
Feedback_ID  →User_ID, Order_ID, Rating_Score, Comments
Order_ID → User_ID
Why it violates BCNF:
Here, 
Order_ID
 determines 
User_ID
 (because an order strictly belongs to one user). But 
Order_ID
 is NOT a candidate key for the Feedback table. This violates BCNF because a non-key attribute is acting as a determinant.
4.5.2 Apply Normalization to BCNF
To convert into BCNF:
Remove the dependency where a non-key determines another attribute.
Separate 
User_ID
 out of the Feedback table.
Relocate 
User_ID
 to the 
Orders
 table where 
Order_ID
 is properly a Candidate/Primary Key
.
Converted to BCNF
4.5 Fourth Normal Form (4NF)
Fourth Normal Form ensures that:
● The table is in 3NF
● There are no multi-valued dependencies
● Independent multi-valued attributes are separated
Menu_Item Table (Not in 4NF)
4.5.1 Identify Dependency
Functional Dependencies:
Item_ID - ->Ingredient
Item_ID - - > Supplier
This indicates that:
One menu item has multiple ingredients.
One menu item can be sourced from multiple independent suppliers.
Ingredients and Suppliers are completely independent of each other.
Why it violates 4NF:
Because they are independent, storing them in the same table forces the database to create redundant, repetitive combinations of every ingredient matched with every supplier for a single item. This violates 4NF due to independent multi-valued dependencies.
Converted to 4NF
4.6 Fifth Normal Form (5NF)
Fifth Normal Form ensures that:
● The table is in 4NF
● There are no join dependencies
● Data can be reconstructed without redundancy
Order System Tables (Not in 5NF)
4.6.1 Identify Dependency
Join dependency exists between: Branch_ID, Item_ID, Supplier_ID
This means:
A specific Branch requires a specific Item.
A specific Item is provided by a specific Supplier.
A specific Supplier delivers to a specific Branch.
Why it violates 5NF: Combining all three into one mega-table creates massive redundancy. However, splitting them into only two tables causes a loss of data regarding who delivers what to where. This represents a cyclic dependency where the information can only be reconstructed accurately by joining three separate relationships.
4.6.2 Apply Normalization to 5NF
To remove the cyclic join dependency:
Decompose the 3-way relationship into three separate 2-way tables:
Branch_Item (Which branch needs which item)
Item_Supplier (Which supplier provides which item)
Supplier_Branch (Which supplier serves which branch)
Maintain the relationships losslessly without redundancy.
Converted to 5NF

IMPLEMENTATION OF CONCURRENCY CONTROL AND RECOVERY MECHANISMS
5.1 Introduction to Transactions
A transaction is a sequence of SQL operations executed as a single logical unit of work. In the Food Quality Monitoring System, transactions ensure that database operations such as placing orders, updating menu items, processing payments, and recording customer feedback are performed reliably and consistently.
5.1.1 Properties of Transactions (ACID)
Atomicity → All operations are completed or none
Consistency → Database remains in a valid state
Isolation → Transactions do not interfere with each other
Durability → Changes are permanent after commit
5.1.2 States of Transaction
Active → Transaction is executing
Partially Committed → Last statement executed
Committed → Successfully completed
Failed → Error occurred
Aborted → Rolled back
5.2 Transaction Control Language (TCL)
5.2.1 SAVEPOINT
A savepoint is used to mark a point within a transaction to which we can later roll back.
5.2.2 COMMIT
Commit permanently saves all changes made during the transaction.
5.2.3 ROLLBACK
Rollback is used to undo changes made during the transaction.

5.4 Concurrency Control
Concurrency control ensures that multiple transactions execute safely without data inconsistency.
5.4.1 Row-Level Locking – SELECT ... FOR UPDATE
USE food_quality_db;
START TRANSACTION;
SELECT * FROM Orders 
WHERE order_id = 101 
FOR UPDATE;
UPDATE Orders

WHERE order_id = 101;
COMMIT;
5.4.2 Concurrency Control – Shared Lock (Write Conflict)
While 
Transaction A
 (the Cashier) holds a Shared Lock to ensure the price remains stable during billing, any attempt by another transaction to modify that specific data will be forced to wait.
Transaction B (Manager Terminal - Attempting a Price Update)
Action:
 The Manager tries to update the price of the "Classic Burger" to reflect a new promotion.
SQL Command:
 
START TRANSACTION; 
-- The manager attempts to change the price of the "Classic Burger"
UPDATE Menu_Item 
SET price = 12.50 
WHERE item_id = 1;
-- STATUS: WAITING... 
Status:
 
Blocked / Waiting
Reasoning:
 Because Transaction A has an active 
Shared Lock (FOR SHARE)
, the database management system (DBMS) recognizes that the data is currently being relied upon for accuracy. A "Write" operation requires an 
Exclusive Lock
, which cannot be granted until all "Shared Locks" on that row are released.
Transaction B
 represents the Manager attempting to modify the burger's price while the Cashier's bill is still being processed.
START TRANSACTION;
-- The manager attempts to increase the price of the "Classic Burger"
UPDATE Menu_Item 
SET price = 12.50 
WHERE item_id = 1;
-- STATUS: [WAITING / BLOCKED]
-- (This query will not execute yet; it hangs while waiting for Transaction A to finish)
5.4.3 Table-Level Locking – LOCK TABLE
LOCK TABLES Menu_Item WRITE;
UPDATE Menu_Item 
SET price = price + 2.00;
UNLOCK TABLES;
Lock Modes
Lock Mode
Description
ROW SHARE
Allows concurrent access; prevents other sessions from locking the table exclusively
ROW EXCLUSIVE
Prevents other sessions from locking in share mode; used by default for DML operations
SHARE
Allows reading but restricts updates and deletes
SHARE ROW EXCLUSIVE
More restrictive than SHARE; prevents most concurrent modifications
EXCLUSIVE
Prevents all other access; full table lock
5.4.3 COMMIT – Permanent Save
COMMIT;
Result:
Changes are permanently saved and all locks are released.
